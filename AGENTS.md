# AGENTS.md

ocpg is a single-file OpenCode plugin (`ocpg.ts`): a Postgres-backed persistent memory layer. It registers a `ctx.session.hook("context", ...)` hook (injects project memories into system context) and a `ctx.session.hook("prompt", ...)` hook (deterministic keyword capture: a trigger phrase like "remember that..." stores the following text verbatim through the normal write path - no LLM) plus `memory_recall` / `memory_remember` / `memory_forget` / `memory_update` tools (via `ctx.tool.transform`). Everything lives in `ocpg.ts`. The module exports **only `default`** (the `Plugin.define` object); test internals are attached to it as `Object.assign(ocpg, { __internals })` - tests do `import ocpg from "../ocpg"; const { __internals } = ocpg;`.

## Run

- Runtime is **Bun only**. Runtime dep is `@opencode/plugin` (V2, matches the opencode release); dev deps are `@biomejs/biome`, `typescript`, `@types/bun`. Targets OpenCode **V2** (`Plugin.define`); V1 plugin code does not run in V2.
- Checks: `bun run check` (biome lint), `bun run typecheck` (`tsc --noEmit`), `bun test`. Commit gating uses the **pre-commit framework** (`.pre-commit-config.yaml`, `repo: local` + `language: system`); enable it per clone with `pre-commit install`. `.github/workflows/check.yml` runs lint, typecheck **and the test suite** on push/PR.
- The biome hook is `repo: local` running `bunx biome check .` rather than the official `biomejs/pre-commit` repo: that repo's latest tag is v2.5.9 while `package.json` pins 2.5.14, and `language: node` would install a second, drifting Biome.
- Both hooks are `pass_filenames: false` and check the whole project. pre-commit stashes unstaged changes, so hooks see only the **staged** snapshot - staging `ocpg.ts` without its `tests/` changes fails typecheck by design.
- **`bun test` is excluded from the pre-commit hook** - it is an integration suite that writes to a real database, so it would break commits on machines without one. **CI does run it**, against a `postgres:18-alpine3.24` service container bootstrapped by `deploy/init/01-init.sh`; the workflow runs the real bootstrap script rather than a copy, so schema drift between CI and `deploy/` fails the build. `psql` comes from the Postgres image via `docker run`, not from whatever client the runner ships.
- The Biome **formatter is currently disabled** (`biome.json`, `formatter.enabled: false`), as is `organizeImports`. The existing source is hand-wrapped, so enabling them reflows ~254 lines. Turn both on in a dedicated formatting-only commit (`bun run format`), never mixed with logic changes.
- Tests: `bun test tests/ocpg.test.ts` (or `bun test`). Uses `bun:test` + `bun:sql` (`SQL` class from `"bun"`), Postgres-specific SQL (`search_vector` FTS, `to_char`) - do not assume portability.

## Test prerequisites (integration tests hit a real DB)

- Live Postgres on `localhost:5432`, database `agent-memory`, table `memories` (columns: `content`, `tags`, `session_id`, `project`, `created_at`, `search_vector`, `memory_type`, `access_count`, `last_accessed_at`, `updated_at`) and the **`pg_trgm` extension** (`CREATE EXTENSION pg_trgm`) - `memory_remember`'s dedup calls `similarity()`.
- DB config resolution: env > defaults; **plugin options are not read** (anything under `"options"` in `opencode.jsonc` is ignored). Env vars: `OCPG_HOST` (default `localhost`), `OCPG_PORT` (5432), `OCPG_USER` (ocpguser), `OCPG_DB` (ocpg), `OCPG_SSL` (`disable`), `OCPG_PASSWORD`, `OCPG_INJECTION` (`recency` opt-out; default is relevance mode). Names are deliberately generic - any Postgres user/db works. The password is **env-only**, never via plugin options or secret-manager CLI fallbacks - the plugin is environment-agnostic and spawns no processes.
- Tests assert `count(*) >= 1` and seed their own fixture project (`/tmp/ocpg-test-fixture`) in `beforeAll` - no hardcoded personal project dir is required any more. `afterAll` cleans every `/tmp/ocpg-test%` project through its **own** SQL client, because the final test closes the shared pool and cleanup through it would silently leak rows.

## Gotchas

- Tests run in file order; the **last test closes the shared pool** (`__internals.sql.close()`, inside the final rate-limit test) to simulate DB failure. Any DB-touching test added after it in the same process will fail - keep it last or restore the connection.
- Several tests assert latency (cold <200ms, warm <5ms) - cache behavior is part of the contract, don't remove the `injectionCache`. It is keyed by **project directory + prompt hash** (relevance mode), so repeated prompts hit and new prompts re-query; writes invalidate every key of the project (32-slot eviction retained).
- An **empty database** caches an empty block and injects nothing - no wrapper, no instruction paragraph, no repeat queries. With any row present, every project gets a block (memories are global).
- The injection query is wrapped in `withDeadline` (1s). It **races, it does not cancel**: Bun documents `query.cancel()`, but on bun 1.4.2 it is a no-op for an in-flight Postgres query (verified against `SELECT pg_sleep(5)` under both `.execute()+.cancel()` and bare `.cancel()`). The caller is freed on time; the abandoned query keeps its pool connection until the server finishes.
- Write caps are abuse guards, not style rules: content 10–4000 chars, ≤10 tags, ≤64 chars per tag. Chosen against a real 485-memory corpus (p95 content 517, p95 5 tags, longest tag 26). Oversized writes are **rejected with the actual size**, never truncated.
- Tool errors returned to the model are generic; the raw driver message (host, user, schema) goes to `console.error` only. `logError(kind, message)` rate-limits **per kind** so a failing recall doesn't mute injection errors.
- `dispose` is **refcounted**. One opencode process evaluates this module once but runs `setup()` once per project location (verified on opencode v2.0.3: four live locations, one module instance), so an unrefcounted `sql.close()` would kill the pool for every other live project.
- The plugin must not spawn processes: resolve credentials/config from env only at init, not per-call.
- Forget/delete/update: `memory_forget(id)` / `memory_update` are **type-aware**: a foreign project's `project_fact` is rejected with a distinct "belongs to another project" message; global types (`preference`, `stack_fact`) are maintainable from any project. The same `visibleRows()` predicate applies. Write-time dedup was removed - `memory_consolidate` handles near-dupes on demand (see below).
- `recall` supports `tags` (`tags @> $1`, AND semantics, served by `idx_memories_tags`) - `search_vector` covers content only, so tags are otherwise unreachable. Directed recall queries use the same OR-of-stemmed-words tsquery as injection (`orTsQuery`), per the bench finding that AND semantics collapse on multi-word queries.
- **Visibility is type-based** (mem-plan.md, deliberate user decision): `preference` and `stack_fact` are global (visible/injectable/deletable/editable everywhere - stack_fact = portable tooling knowledge); `project_fact` is visible **only from its origin project** unless the caller passes `global: true` on recall (injection has no flag - other projects' project_fact never surface as ambient context). The predicate lives in one place: `visibleRows()`, shared by recall and both injection builders. A blanket-global design and a user-scope sentinel (`OCPG_USER_ID`) each existed briefly and were replaced by this.
- Injection is **relevance-based** by default: the latest user message becomes an OR-of-stemmed-words `to_tsquery` over **all memories** (`OCPG_INJECTION=recency` restores last-5). The cache is keyed `directory\0prompt-hash`; `invalidateInjection` clears every prompt key of the directory. Prompt hooks pass `extractPromptQuery(event.messages)`. FTS is content-only - tags stay an explicit recall filter (`array_to_string` is STABLE, so tags cannot join the generated `search_vector`).
- Injection orders `preference` rows first, then recency **in recency mode / no-match fallback**; `memory_type` is defaulted (`project_fact`), never required, and the vocabulary is mirrored by the DB CHECK constraint.
- Writes **never reject** on duplicates - there is no `force` param. Near-dupes (trigram similarity >= 0.8, global) are handled by `memory_consolidate`: on-demand, deterministic (keeps the newest of each cluster, deletes the rest), returning the removed texts so the calling agent can merge unique facts back via `memory_update`. Merging is the agent's job - the plugin makes no model calls. Injection fetches a 20-row candidate slice and collapses near-dupes in TS (`collapseDupes`, char-trigram Jaccard) so duplicate writes cannot fill the 5 slots between consolidations. Requires `idx_memories_trgm` (gin on `content gin_trgm_ops`) for the consolidate self-join.
- Undirected recall is plain recency (preferences first) - a recency x frequency gravity blend was tried and removed: bumping exactly the returned top-5 is a rich-get-richer loop that pinned corpus rows. The fire-and-forget bump on recall stays (data collection); no ranking consumes `access_count` today.
- `memory_update` sets `updated_at` and deliberately never bumps `created_at`; it has no dedup fall-through by design.
- SQLSTATE `42883` (undefined_function) is special-cased in `toolError` to name the missing `pg_trgm` extension; every other DB error returns a generic message to the model.
- Injected memory blocks truncate content to 600 chars.
- Deployment: published to npm as `@dzhi/ocpg` via GitHub Actions trusted publishing (`.github/workflows/publish.yml`, OIDC - tag-push `v*` or manual dispatch); the workflow fails unless the tag equals the `package.json` version, so bump the version before tagging.
- opencode loads the plugin via the npm spec; the GitHub `user/repo` spec triggers opencode's DEP0169 `url.parse()` resolver bug. opencode installs only deps declared in `package.json` into its plugin cache - an undeclared import makes the plugin silently fail to load (reported only via an event-bus toast, never in logs).
- Keep the module exports limited to `default` (the `Plugin.define` object); extend `__internals` via the existing `Object.assign` on the default export.
- Bun SQL array params need the element type: `sql.array(values, "text")` - bare `sql.array(values)` encodes text[] with quoted elements (each tag stored as `"tag"` with literal quotes), and a raw JS array throws `malformed array literal`.
- Never construct `new SQL("postgres://…")` from a URL string - under opencode's runtime it emits the DEP0169 `url.parse()` warning at startup. Use the options-object constructor via `makeSql()`.
- `deploy/` - standalone Postgres for users: `compose.yaml` (hardened, localhost-only) + `init/01-init.sh` bootstraps the `memories` table into the `POSTGRES_DB` database on first boot (any db name); setup docs in `deploy/README.md`. `init/01-init.sh` runs **only on first boot** - `deploy/README.md` carries the idempotent upgrade block for existing installs; when the schema changes, update both.
- `bench/` - retrieval-strategy benchmark on synthetic, seeded bench DBs (`agent-memory-bench-<size>`; needs CREATEDB): `bun run bench:generate` then `bun run bench`. Accuracy is measurable because every memory has a topic (ground truth by construction); paraphrase queries use leak-checked synonyms that appear nowhere in the corpus - **paraphrase recall is the pgvector decision number** (0.000 today). `fts-or (prod)` runs the exact production query via `__internals.buildRelevanceQuery`/`buildRecencyQuery` - when changing the injection SQL, those builders are the single source both ocpg and bench share; do not copy SQL into the bench. Bench findings so far live in `bench/README.md`.

## Git / release workflow

- Never commit to `main` - feature branches only; the user pushes, merges, and tags.
- A commit that ships to npm is incomplete without its `package.json` version bump in the same branch; the publish workflow (and the `tag-version-match` pre-push hook) reject tags that don't match the version on the tagged commit.
- Tag the merge commit on `main` (after the PR merges), never the branch head - tags must point into main's history.
