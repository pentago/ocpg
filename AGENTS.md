# AGENTS.md

ocpg is a single-file OpenCode plugin (`ocpg.ts`): a Postgres-backed persistent memory layer. It registers a `ctx.session.hook("context", ...)` hook (injects project memories into system context) and a `ctx.session.hook("prompt", ...)` hook (deterministic keyword capture: a trigger phrase like "remember that..." stores the following text verbatim through the normal write path - no LLM) plus `memory_recall` / `memory_remember` / `memory_forget` / `memory_update` / `memory_consolidate` tools (via `ctx.tool.transform`). Everything lives in `ocpg.ts`. The module exports **only `default`** (the `Plugin.define` object); test internals are attached to it as `Object.assign(ocpg, { __internals })` - tests do `import ocpg from "../ocpg"; const { __internals } = ocpg;`.

## Run

- Runtime is **Bun only**. Runtime dep is `@opencode/plugin` (V2, matches the opencode release); dev deps are `@biomejs/biome`, `typescript`, `@types/bun`. Targets OpenCode **V2** (`Plugin.define`); V1 plugin code does not run in V2.
- Checks: `bun run check` (biome lint), `bun run typecheck` (`tsc --noEmit`), `bun test`. Commit gating uses the **pre-commit framework** (`.pre-commit-config.yaml`, `repo: local` + `language: system`); enable it per clone with `pre-commit install`. `.github/workflows/check.yml` runs lint, typecheck **and the test suite** on push/PR.
- The biome hook is `repo: local` running `bunx biome check .` rather than the official `biomejs/pre-commit` repo: that repo's latest tag is v2.5.9 while `package.json` pins 2.5.14, and `language: node` would install a second, drifting Biome.
- Both hooks are `pass_filenames: false` and check the whole project. pre-commit stashes unstaged changes, so hooks see only the **staged** snapshot - staging `ocpg.ts` without its `tests/` changes fails typecheck by design.
- **`bun test` is excluded from the pre-commit hook** - it is an integration suite that writes to a real database, so it would break commits on machines without one. **CI does run it**, against a `pgvector/pgvector:0.8.6-pg18-trixie` service container bootstrapped by `deploy/init/01-init.sh`; the workflow runs the real bootstrap script rather than a copy, so schema drift between CI and `deploy/` fails the build. `psql` comes from the same pgvector image via `docker run`, not from whatever client the runner ships.
- The Biome **formatter is currently disabled** (`biome.json`, `formatter.enabled: false`), as is `organizeImports`. The existing source is hand-wrapped, so enabling them reflows ~254 lines. Turn both on in a dedicated formatting-only commit (`bun run format`), never mixed with logic changes.
- Tests: `bun test tests/ocpg.test.ts` (or `bun test`). Uses `bun:test` + `bun:sql` (`SQL` class from `"bun"`), Postgres-specific SQL (`search_vector` FTS, `to_char`) - do not assume portability.

## Test prerequisites (integration tests hit a real DB)

- Live Postgres on `localhost:5432`, database `agent-memory`, table `memories` (columns: `content`, `tags`, `session_id`, `project`, `created_at`, `search_vector`, `embedding`, `memory_type`, `access_count`, `last_accessed_at`, `updated_at`) and the **`pg_trgm` extension** (`CREATE EXTENSION pg_trgm`) - `memory_consolidate`'s wording pass computes trigram similarity in TS, but the schema still requires the extension (`idx_memories_trgm`) and `toolError` names it specifically on SQLSTATE 42883. The `embedding vector(1024)` column (pgvector) is optional for the suite: hybrid integration tests probe for it plus a reachable Ollama at module load and `test.skipIf` otherwise - so CI (no Ollama) proves keyword-only integrity and a migrated local DB with Ollama proves the hybrid path.
- DB config resolution: env > defaults; **plugin options are not read** (anything under `"options"` in `opencode.jsonc` is ignored). Env vars: `OCPG_HOST` (default `localhost`), `OCPG_PORT` (5432), `OCPG_USER` (ocpguser), `OCPG_DB` (ocpg), `OCPG_SSL` (`disable`), `OCPG_PASSWORD`, `OCPG_INJECTION` (`recency` opt-out; default is relevance mode), plus the embedding client: `OCPG_OLLAMA_HOST` (`localhost`), `OCPG_OLLAMA_PORT` (11434), `OCPG_EMBED_MODEL` (`bge-m3`). Names are deliberately generic - any Postgres user/db works. The password is **env-only**, never via plugin options or secret-manager CLI fallbacks - the plugin is environment-agnostic and spawns no processes.
- Tests assert `count(*) >= 1` and seed their own fixture project (`/tmp/ocpg-test-fixture`) in `beforeAll` - no hardcoded personal project dir is required any more. `afterAll` cleans every `/tmp/ocpg-test%` project through its **own** SQL client, because the final test closes the shared pool and cleanup through it would silently leak rows.

## Gotchas

- Tests run in file order; the **last test closes the shared pool** (`__internals.sql.close()`, inside the final rate-limit test) to simulate DB failure. Any DB-touching test added after it in the same process will fail - keep it last or restore the connection.
- Several tests assert latency (cold <200ms, warm <5ms) - cache behavior is part of the contract, don't remove the `injectionCache`. It is keyed by **project directory + prompt hash** (relevance mode), so repeated prompts hit and new prompts re-query; writes invalidate every key of the project (32-slot eviction retained).
- An **empty database** caches an empty block and injects nothing - no wrapper, no instruction paragraph, no repeat queries. With any row present, every project gets a block (memories are global).
- The injection query is wrapped in `withDeadline` (1s). It **races, it does not cancel**: Bun documents `query.cancel()`, but on bun 1.4.2 it is a no-op for an in-flight Postgres query (verified against `SELECT pg_sleep(5)` under both `.execute()+.cancel()` and bare `.cancel()`). The caller is freed on time; the abandoned query keeps its pool connection until the server finishes.
- Write caps are abuse guards, not style rules: content 10–4000 chars, ≤10 tags, ≤64 chars per tag. Chosen against a real 485-memory corpus (p95 content 517, p95 5 tags, longest tag 26). Oversized writes are **rejected with the actual size**, never truncated.
- Tool errors returned to the model are generic; the raw driver message (host, user, schema) goes to `console.error` only. `logError(kind, message)` rate-limits **per kind** so a failing recall doesn't mute injection errors.
- `dispose` is **refcounted**. One opencode process evaluates this module once but runs `setup()` once per project location (verified on opencode v2.0.3: four live locations, one module instance), so an unrefcounted `sql.close()` would kill the pool for every other live project.
- The plugin must not spawn processes: resolve credentials/config from env only at init, not per-call.
- Forget/delete/update: `memory_forget(id)` / `memory_update` are **type-aware**: a foreign project's `project_fact` is rejected with a distinct "belongs to another project" message; the global type (`stack_fact`) is maintainable from any project. The same `visibleRows()` predicate applies. Write-time dedup was removed - `memory_consolidate` handles near-dupes on demand (see below).
- `recall` supports `tags` (`tags @> $1`, AND semantics, served by `idx_memories_tags`) - `search_vector` covers content only, so tags are otherwise unreachable. Directed recall queries use the same OR-of-stemmed-words tsquery as injection (`orTsQuery`), per the bench finding that AND semantics collapse on multi-word queries.
- **Visibility is type-based** (mem-plan.md, deliberate user decision): `stack_fact` is global (visible/injectable/deletable/editable everywhere - portable tooling knowledge); `project_fact` is visible **only from its origin project** unless the caller passes `global: true` on recall (injection has no flag - other projects' project_fact never surface as ambient context). The predicate lives in one place: `visibleRows()`, shared by recall and both injection builders. A blanket-global design and a user-scope sentinel (`OCPG_USER_ID`) each existed briefly and were replaced by this. The `preference` type (also global) was removed entirely on 2026-09-19 - see the dedicated bullet below.
- Injection is **relevance-based** by default: the latest user message becomes an OR-of-stemmed-words `to_tsquery` over **all memories** (`OCPG_INJECTION=recency` restores last-5). The cache is keyed `directory\0prompt-hash`; `invalidateInjection` clears every prompt key of the directory. Prompt hooks pass `extractPromptQuery(event.messages)`. FTS is content-only - tags stay an explicit recall filter (`array_to_string` is STABLE, so tags cannot join the generated `search_vector`).
- Retrieval is **hybrid** (keyword + embeddings): with a non-empty prompt/query, `embed()` calls the host Ollama concurrently with the keyword query and the two ranked lists merge via `hybridMerge` - the vector list's top 2 rows are **reserved unconditionally**, the rest is `rrfMerge` (RRF k=60, keyed on content) minus the picks (bench/rrf-slots.ts: R=2 is the free knee; weighting the vector side was benched and rejected - rows present in both lists win at any weight). `reserved=0` or an empty/failed vector list degenerates to plain RRF or keyword-only; recall reserves `min(2, floor(limit/2))` so tiny limits can't displace a direct keyword hit. Every embedding failure degrades to keyword-only: `embed()` never rejects (null on any error, rate-limited `embed` log kind), and a failed vector query (e.g. pre-migration DB without the column) is caught per-call (`embed-query` kind). The recency fallback now fires only when **both** halves are empty - the vector half alone counts as a signal, which is the zero-overlap paraphrase case the feature exists for.
- Embedding latency, measured on the host (RTX 5070): warm bge-m3 ~20ms, cold model load ~2-3s (over the 1s injection deadline). So `setup()` fires a fire-and-forget warm-up embed and every request passes `keep_alive: "30m"`; the query-path timeout is 750ms (races the warm-up or a wedged daemon → keyword-only), the write path gets 15s (tolerates cold loads). Writes embed fire-and-forget via `embedAndStore` (remember + memory_update - an update MUST re-embed or the vector goes stale); a row with NULL embedding is keyword-only until `bun run backfill` (`deploy/backfill.ts`, idempotent, checks column dimension against the model first). The bench DBs' legacy MiniLM column is literally named `embedding` (384-dim) - a dimension collision the backfill refuses to touch.
- Injection ordering is now **plain recency** (`ORDER BY created_at DESC`) in recency mode / the no-match fallback - it was `ORDER BY (memory_type = 'preference') DESC, created_at DESC` before `preference` was removed (2026-09-19); there is nothing left to rank ahead of recency. `memory_type` is defaulted (`project_fact`), never required, and the vocabulary is mirrored by the DB CHECK constraint.
- **`preference` type removed (2026-09-19)**: its only real justification (a place for standing rules that apply everywhere) is better served by a global `AGENTS.md` - always in context, deterministic, not subject to relevance ranking. `MEMORY_TYPES` is now `["stack_fact", "project_fact", "episodic"]`; a write with `type: "preference"` is rejected like any other unknown value (`resolveMemoryType` falls back to `project_fact`). Existing `preference` rows in the live personal DB were deleted outright (user's explicit call, not migrated to `stack_fact`) and the CHECK constraint was tightened to match; `deploy/init/01-init.sh` and `deploy/README.md`'s upgrade block were updated in lockstep, and `bench/generate.ts`'s synthetic-DB constraint dropped it too.
- Writes never reject on duplicates: `memory_remember` is a plain validate-then-insert (no write-time dedup) - duplicate detection is `memory_consolidate`'s job, run on demand. Injection fetches a 20-row candidate slice and collapses near-dupes in TS (`collapseDupes`, char-trigram Jaccard) so duplicate writes cannot fill the 5 slots between consolidations.
- `memory_consolidate` runs two passes and merges their reports: a **wording** pass (trigram similarity over content, unchanged since it first shipped - greedy newest-first clustering, a row joins the first existing cluster whose representative it near-dupes) and a **meaning** pass (embedding cosine similarity via pgvector's `<=>`, `CONSOLIDATE_EMBED_THRESHOLD` 0.83 - catches the same fact stated in completely different words, which trigram structurally cannot reach). Each pass keeps the newest of every multi-member cluster and deletes the rest, capped at 25 clusters per pass per run; the wording pass runs to completion first, so the meaning pass only sees whatever survived it. Only embedded rows participate in the meaning pass (Ollama down at write time = simply not a candidate, same degrade posture as everywhere else). Both passes report `[wording]` / `[meaning]` per removed group so the calling agent can tell "found by wording" from "found by meaning."
- Mutual visibility for the meaning pass mirrors `visibleRows()`: two rows may only cluster if neither is a `project_fact` from a different project than the other (`mutuallyVisible()` in `ocpg.ts`) - a consolidation pass must not delete/merge across a boundary `memory_forget`/`memory_update` already refuse to cross. The wording pass has no such guard (pre-existing, unchanged; no test exercises cross-project wording collisions).
- `CONSOLIDATE_EMBED_THRESHOLD` (0.83) was calibrated against the same hand-labeled pairs the (now-removed) judge bench used: true duplicates clustered 0.78-0.96 (mean .88), distinct-but-related pairs topped out at 0.76 (mean .58), and "update" pairs (a fact superseding an older one) sat in between (0.57-0.87) and overlap both - no threshold cleanly separates updates from duplicates, so 0.83 was picked to sit clear of every distinct pair (protecting the failure mode that matters: never delete a genuinely unique fact) while still catching most duplicates and roughly half the update pairs (deleting the stale side of a superseded fact is an acceptable, reviewable outcome - the removed text always comes back in the report).
- **Meaning-pass exclusion, real-corpus audit (2026-09-19)**: running the meaning pass against the live corpus for the first time surfaced 11 wrong merges out of 32 - all templated, auto-generated content (background-task status logs from the team/subagent system, session-compaction summaries, per-app migration checklist entries) where cosine similarity stays high across GENUINELY DIFFERENT facts (different task ids, team members, sessions, apps) because only a few words vary against a shared boilerplate sentence. The `auto_capture` tag was tried first as an exclusion filter and rejected: it sits on ~90% of both correct AND incorrect merges in the real corpus, so excluding by tag would gut the pass. Content-pattern matching (`isTemplatedAutoLogPair`/`isTemplatedAutoLog` in `ocpg.ts`: `background task bg_`, `session compacting for project`, `For APP <n> (`) has zero overlap with any confirmed-correct merge and fixed 9 of the 11. The remaining 2 (natural-language pairs sitting at ~0.84 cosine, e.g. two genuinely different systemd unit files described in structurally parallel sentences) are an accepted residual: raising the threshold to exclude them would also have excluded 3 confirmed-correct merges in the same audit, confirming no single threshold separates this case from true duplicates.
- The exclusion predicate has a permanent regression net (`tests/ocpg.test.ts`, "consolidate: isTemplatedAutoLog predicate") that runs `isTemplatedAutoLog` directly via `__internals` against representative real-corpus strings for all three template shapes plus real confirmed-correct natural-language merges as negative controls - fast, no Ollama/hybridReady gate (the predicate only reads `content`), so a future refactor that widens or narrows the pattern is caught even on a machine with no embedding setup. Two more `hybridReady`-gated integration tests (session-compaction and per-app template shapes) mirror the existing background-task one end-to-end; their synthetic fixtures deliberately avoid a shared repeated token (a first attempt reusing one marker string in both halves of a pair pushed trigram Jaccard just over 0.8, so the *wording* pass caught them before the meaning pass was ever exercised - not a bug, but a reminder that fixture text needs the same low textual overlap the real audit pairs had).
- **Detail cross-check for the meaning pass (2026-09-20)**: the QQP stress test above found no `CONSOLIDATE_EMBED_THRESHOLD` value cleanly separates duplicate from distinct at scale, and manual review pinned the specific failure mode - two texts phrased almost identically but differing in one specific number/path/name (a rate limit of 100 vs 500 requests/minute; a system-level `/etc/systemd/system/` vs a user-level `~/.config/systemd/user/` unit). `extractDetails()`/`detailConflicts()` in `ocpg.ts` add a second, independent, regex-only signal (no model call, consistent with the judge-model removal) that gates every meaning-pass candidate pair on top of the existing cosine threshold: numbers, paths, and capitalized proper nouns (skipping the sentence-initial word, since every sentence starts capitalized regardless of content) are extracted from both sides, and a category **conflicts** only when both sides have values in it AND those values are disjoint - absence on one side is never a conflict. A conflicting pair is pulled OUT of its cluster's auto-merge (the rest of an otherwise-clean cluster still merges) and reported as a new `[meaning-uncertain]` line instead of `[meaning]` - not deleted, requires an explicit `memory_update`/`memory_forget` from the caller. Re-scored against the same QQP sample (`bench/qqp-consolidate.ts`, `bench/README.md`'s "Detail cross-check" section): FPR only drops 0.200 -> 0.192 and 2.1% of true duplicates get routed to review instead of silently merged - a small effect, expected and documented as such, because QQP question pairs mostly carry no numbers/paths/names to conflict on in the first place (the same genre-scoping caveat as the original QQP test); the check is aimed at ocpg's own real corpus, which has far more of that kind of specific detail per memory than a Quora question does. Proper-noun extraction is capitalization-based only and documented as the part most likely to need iteration (e.g. it cannot catch a lowercase technical name like `bge-m3`).
- **Detail cross-check re-test on ocpg-shaped content (2026-09-20, confirms the corpus-mismatch read above)**: `bench/ocpg-shaped-consolidate.ts` builds an 808-pair labeled corpus IN-PROCESS from the same 40-topic infra vocabulary `bench/generate.ts` uses, programmatically injecting numbers/paths/proper-noun values so `update-*` pairs reproduce the two real incidents' exact shape (same sentence, one value swapped). Result decisively confirms the QQP finding was a corpus mismatch, not a weak check: baseline FPR at 0.83 is actually WORSE than QQP's (0.370 vs 0.200, because this corpus is adversarially built to fool cosine similarity), but the detail check drops it to 0.005 - 161/163 false positives (98.8%) correctly rerouted to `[meaning-uncertain]`, and every `update-*` category pair that reached the threshold was caught (0 clean merges across all `update-*` rows). False-negative cost stays small (5/316 true duplicates, 1.6%, blocked to review). The `fn-stress` hand-picked set (8 pairs, genuine near-duplicates differing only in formatting) found a real, honestly-documented gap: comma grouping (`1,000` vs `1000`), a dropped trailing zero (`2.5.0` vs `2.5`), a trailing slash, and letter case (`Jira` vs `JIRA`) all get wrongly blocked - `extractDetails` does no number/path/name normalization, exactly the "most likely to need iteration" caveat already documented above. A spelled-out number ("three replicas") and a unit-suffixed number (`300s` vs `300 seconds`) correctly pass through by the absence/exact-token-match rules, proving those design choices work as intended too. Full tables and readings in `bench/README.md`'s "Detail cross-check re-test on ocpg-shaped content" section.
- Undirected recall is plain recency - a recency x frequency gravity blend was tried and removed: bumping exactly the returned top-5 is a rich-get-richer loop that pinned corpus rows. The fire-and-forget bump on recall stays (data collection); no ranking consumes `access_count` today.
- **Cross-session recall signal (2026-09-20)**: a second, independent tiebreak that DOES get consumed by ranking, unlike `access_count` - the difference is what each counts. A new `memory_recalls(memory_id, session_id, recalled_at)` table with PRIMARY KEY `(memory_id, session_id)` records which sessions have recalled a memory; `COUNT(DISTINCT session_id)` (not row count) is the signal, so repeated recalls from ONE session collapse to one data point instead of compounding - the exact property `access_count`'s reverted ranking attempt lacked. `recall()` upserts into it fire-and-forget (same pattern as the `access_count` bump, `ON CONFLICT DO NOTHING`), gated on `ctx.sessionID` being present (`__internals` callers that omit it simply skip the record, never throw). `crossSessionJoin`/`crossSessionBoost` in `ocpg.ts` add `LEAST(cross_session_count, 5) * 0.002` to `buildRelevanceQuery`'s ORDER BY (on top of the existing same-project +0.01) and to `recall()`'s directed-query ORDER BY (which has no same-project boost to begin with) - capped and weighted well below the same-project boost so it only breaks near-ties. Bench-verified first (`bun bench/cross-session.ts`, `bench/README.md`): recall/precision unchanged at 485/4970/49980 rows, MRR improves slightly (+0.002-0.003), and the specific failure mode is directly demonstrated, not just argued - spamming one memory 50x from a single session moves neither its `cross_session_count` nor its rank past what the first (genuinely new) recall already caused, while distinct sessions do move it further. `memory_recalls` is a mandatory additive migration (like `memory_type`/`access_count` before it, not an optional/probed feature like the embedding column) - `deploy/init/01-init.sh`, `deploy/README.md`'s upgrade block, and `bench/generate.ts`'s DDL all gained it in lockstep, since `buildRelevanceQuery` is shared verbatim between production and the bench harness.
- `memory_update` sets `updated_at` and deliberately never bumps `created_at`; it has no dedup fall-through by design.
- SQLSTATE `42883` (undefined_function) is special-cased in `toolError` to name the missing `pg_trgm` extension; every other DB error returns a generic message to the model.
- Injected memory blocks truncate content to 600 chars.
- Deployment: published to npm as `@dzhi/ocpg` via GitHub Actions trusted publishing (`.github/workflows/publish.yml`, OIDC - tag-push `v*` or manual dispatch); the workflow fails unless the tag equals the `package.json` version, so bump the version before tagging.
- opencode loads the plugin via the npm spec; the GitHub `user/repo` spec triggers opencode's DEP0169 `url.parse()` resolver bug. opencode installs only deps declared in `package.json` into its plugin cache - an undeclared import makes the plugin silently fail to load (reported only via an event-bus toast, never in logs).
- Keep the module exports limited to `default` (the `Plugin.define` object); extend `__internals` via the existing `Object.assign` on the default export.
- Bun SQL array params need the element type: `sql.array(values, "text")` - bare `sql.array(values)` encodes text[] with quoted elements (each tag stored as `"tag"` with literal quotes), and a raw JS array throws `malformed array literal`.
- Never construct `new SQL("postgres://…")` from a URL string - under opencode's runtime it emits the DEP0169 `url.parse()` warning at startup. Use the options-object constructor via `makeSql()`.
- `deploy/` - standalone Postgres for users: `compose.yaml` (hardened, localhost-only; pgvector image plus an optional CPU-only `ollama` service as the embedding backend - GPU reservation block is commented, unneeded at ocpg's embed rates) + `init/01-init.sh` bootstraps the `memories` table into the `POSTGRES_DB` database on first boot (any db name); setup docs in `deploy/README.md`. `init/01-init.sh` runs **only on first boot** - `deploy/README.md` carries the idempotent upgrade block for existing installs; when the schema changes, update both.
- `bench/` - retrieval-strategy benchmark on synthetic, seeded bench DBs (`agent-memory-bench-<size>`; needs CREATEDB): `bun run bench:generate` then `bun run bench`. Accuracy is measurable because every memory has a topic (ground truth by construction); paraphrase queries use leak-checked synonyms that appear nowhere in the corpus - **paraphrase recall is the pgvector decision number**. `fts-or (prod)` runs the exact production query via `__internals.buildRelevanceQuery`/`buildRecencyQuery` - when changing the injection SQL, those builders are the single source both ocpg and bench share; do not copy SQL into the bench. Embedding strategies (pgvector + host ollama) live in `bench/embed.ts` (`bun run bench:embed`) against the throwaway container from `bench/compose.yaml` (port 5433, full `OCPG_USER/PORT/PASSWORD` override required - direnv exports the real DB's vars); query mix/scoring are shared with `run.ts` via `bench/lib.ts`. `bench/embed.ts` also carries the `hybrid-rrf` strategy that validated the shipped hybrid (recall >= both parents at every size; its vector SQL is model-parameterized by design, so it cannot import the fixed-column `buildVectorQuery`). `bench/ollama-backends.ts` (`bun run bench:backends`) compares embedding BACKENDS (host GPU vs containerized CPU ollama) on the plugin's real paths - cold load, warm embed, batch-32, end-to-end hybrid query - against the live DB, read-only. Merge-variant sweeps: `bench/rrf-weights.ts` (vector weighting: no win, equal weight stays) and `bench/rrf-slots.ts` (reserved vector slots: R=2 is free on synthetic, R=3 closest to embedding-only on real paraphrases). `bench/judge.ts` and `bench/capture.ts` (the former smart-write/compaction-capture gates) were deleted along with the judge model they tested; their historical numbers stay in `bench/README.md` as a record. `bench/generate-thesaurus.ts`, `bench/thesaurus/` and the `fts-or-thesaurus`/`fts-phrase-thes`/`fts-or-plus-thesaurus` strategies in `run.ts` (plus the `bench:thesaurus` package.json script and `THESAURUS_DDL` in `generate.ts`) were removed 2026-09-19 the same way: the thesaurus was a competing candidate for closing the paraphrase gap, explored 2026-09-17 before the embedding/hybrid results won and shipped instead - its historical numbers stay in `bench/README.md`, marked superseded.
- **Supersede tracking (2026-09-21)**: real usage feedback identified that a corrected/reverted memory (judge model, `preference` type) used to stay in the table exactly as visible as a current fact - only a *later*, unrelated memory narrated the revert in prose, and recall/injection had no reason to always surface both together, so an agent could act on the stale one alone. `memory_remember` gained an optional `supersedes: <id>` argument: `remember()` inserts the new row and sets the target's `superseded_by` column in one `sql.begin` transaction - a rejected supersede (wrong project, or a nonexistent id) throws a dedicated `SupersedeError` inside the transaction, rolling back the insert too, so the failure mode is "nothing happened" rather than an orphaned, unlinked insert. The project-boundary rule mirrors `memory_forget`/`memory_update` exactly (reuses `visibleRows()` for the ownership check on the UPDATE). A new `notSuperseded()` predicate (`superseded_by IS NULL`) is layered ON TOP of `visibleRows()`, not merged into it, and wired into `buildRecencyQuery`/`buildRelevanceQuery`/`buildVectorQuery` and `recall()`'s default path only - `forget()`/`updateMemory()` deliberately keep using bare `visibleRows()` so a superseded row stays reachable to delete outright or fix a bad link. `memory_recall` gained `includeSuperseded` (default false) to surface history on demand, annotating each such row with `[superseded by #<id>]`; injection has no equivalent override by design (ambient context should never carry stale facts). `memory_consolidate`'s candidate queries (both the wording pass's initial SELECT and the meaning pass's pair/row queries) exclude `superseded_by IS NOT NULL` rows entirely - a superseded row is an already-resolved decision, not an accidental duplicate to guess about. `ON DELETE SET NULL` on the FK means forgetting the *superseding* memory un-supersedes the old one instead of leaving a dangling reference; no retroactive linking was done for the two real historical examples that motivated this (out of scope, optional cleanup later). Additive migration - `superseded_by integer REFERENCES memories(id) ON DELETE SET NULL`, nullable, no CHECK constraint - applied in lockstep to `deploy/init/01-init.sh` and `deploy/README.md`'s upgrade block.

## Git / release workflow

- Never commit to `main` - feature branches only; the user pushes, merges, and tags.
- A commit that ships to npm is incomplete without its `package.json` version bump in the same branch; the publish workflow (and the `tag-version-match` pre-push hook) reject tags that don't match the version on the tagged commit.
- Tag the merge commit on `main` (after the PR merges), never the branch head - tags must point into main's history.
